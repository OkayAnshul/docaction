# Experience

## Information architecture

The app has **three destinations and one flow**.

```
┌─ Home ──────────────────────────────────────────────────────────────────────┐
│  └──▶ Import ──▶ Processing ──▶ [Questions] ──▶ Review ──▶ Confirm ──▶ Done │  full screen,
│                       └── failure ──▶ Recovery ──────────┘                  │  above the bar
├─ My week ──▶ slot editor                                                    │
├─ History ──▶ undo                                                           │
└─────────────────────────────────────────────────────────────────────────────┘
   Settings ──▶ Privacy          reached from Home, not from the bar
```

**Revised 2026-08-18.** This section previously specified four places and stated flatly that
there was no bottom navigation bar, on the grounds that it would advertise Settings and History
as equals to the thing people came to do. That reasoning still holds for Settings — which is why
Settings and Privacy are reached from Home and are not destinations — but it did not survive
Timetable becoming something you *edit* rather than something you look at. A weekly schedule the
user maintains is a place they return to, and burying the way back to it inside the screen whose
job is starting an import made it feel like a by-product of importing.

**The import flow is not a tab.** It runs full-screen and the bar disappears for its duration.
That is a safety property, not a layout preference: the flow is a linear machine ending in a
calendar write, and a persistent bar would let someone leave a Confirm half-answered and return
to one whose write had already happened — the double-import trap this design has always avoided.

### Navigation model

- The import flow is a **single task stack**. Predictive back moves one step back within it.
- Backing out of Review prompts to discard — the user has done work there.
- Backing out of Processing cancels the operation and says so.
- After a successful write, back returns Home, not to Review. The task is complete; re-entering
  a completed review is a trap that invites double-importing.
- Back from a tab returns to Home rather than leaving the app. Back from Home exits, as the
  platform expects.
- There is exactly one route to each destination. Home briefly carried its own "My Timetable"
  button alongside the bar; two doors to one room is clutter on the screen that can least
  afford it.

## UX principles

### 1. The document is the subject, not the app

Screens are named after what the user has, not after what the software does. "42 classes found",
not "Extraction complete". "Review timetable", not "Results".

### 2. State the outcome before the mechanism

Every screen leads with the answer. `42 classes found` is the headline; `CSE · Semester 5 ·
Section B` is the subtitle; the list is below. The user should be able to decide whether to
continue from the first line.

### 3. Uncertainty is visible, specific, and actionable

Never "some items may be incorrect". Always "2 items need your attention", tappable, filtered.
A warning the user cannot act on is noise.

### 4. Reversibility beats confirmation dialogs

One good confirmation before the write, plus a real undo after it. Not four dialogs.

### 5. Progress is honest

If we know the page count, show `Page 12 of 84`. If we genuinely don't know, use an
indeterminate indicator. Never a fake determinate bar — users have learned to distrust them, and
distrust is the one thing this product cannot afford.

### 6. The interface gets quieter as confidence rises

High-confidence rows are plain. Only the exceptions get visual weight. A screen where all 42
rows shout is a screen where nothing is read.

## Screen specifications

### Home

**Job:** get the user into the import flow in one tap, and show them anything left unfinished.

```
┌─────────────────────────────────────┐
│  DocAction              ⏱   ⚙︎      │   history, settings
│                                     │
│  Good afternoon                     │   time-aware, not a greeting gimmick —
│  Turn information into action.      │   it dates the session for the History mental model
│                                     │
│  ┌───────────────────────────────┐  │
│  │                               │  │
│  │       + Add document          │  │   single dominant CTA, ~64dp tall
│  │                               │  │
│  └───────────────────────────────┘  │
│                                     │
│  ⚠  2 items need your attention     │   only rendered if true
│     Timetable.pdf · 20 min ago      │
│                                     │
│  Recent                             │
│  ─────────────────────────────      │
│  📄  Exam Schedule.pdf              │
│      8 events · added today         │
│                                     │
│  📊  Timetable.xlsx                 │
│      42 classes · added Aug 3       │
└─────────────────────────────────────┘
```

Rules:
- The pending-review banner appears **only** when an unfinished import exists. No empty slot.
- Recent shows at most 3. History holds the rest.
- No statistics, no streaks, no dashboard. Nobody wants to know how many documents they've processed.

**Empty state** (first run):

```
        Nothing here yet.

  Give me a timetable, schedule or
  document and I'll turn it into
  something useful.

    ┌───────────────────────────┐
    │   Add your first document │
    └───────────────────────────┘
```

### Import

A bottom sheet, not a screen. It is a choice, not a destination.

```
  Add document
  ─────────────────────────────
  📁  Files            PDF, spreadsheet, CSV
  🖼️  Photos           screenshot or photo
  📷  Camera           scan a printed schedule
  📋  Paste text
```

Files opens `ACTION_OPEN_DOCUMENT`. Photos opens the Android Photo Picker — **no storage
permission is requested**, and this is worth the extra work because "why does this need my
photos?" is a top-five complaint in the scanner category.

### Processing

```
┌─────────────────────────────────────┐
│  ✕                                  │   cancel is always present, top-left
│                                     │
│  Analysing your timetable…          │
│                                     │
│  ✓  Reading document                │
│  ✓  Detecting structure             │
│  ✓  Finding dates                   │
│  ●  Finding times                   │   current stage, subtle pulse
│  ○  Building schedule               │
│                                     │
│  Page 12 of 84                      │   only when genuinely known
│  ▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░              │
│                                     │
│              [ Cancel ]             │
└─────────────────────────────────────┘
```

The stage list is real — each line corresponds to an actual pipeline stage emitting progress
(see [07-pipeline.md](07-pipeline.md)). If a stage is skipped (no OCR needed), it is not shown.
We do not display stages we aren't running.

Cancellation is immediate and honest: *"Cancelled. Nothing was changed."*

### Disambiguation

Shown only when the pipeline genuinely cannot proceed. Each question is a full screen with one
question, because these decisions are consequential and burying them in a list guarantees
mis-taps.

**Date format:**
```
  Which date is this?

  The document writes dates like 03/04/2026.
  We can't tell which part is the month.

  ┌───────────────────────────────────┐
  │  3 April 2026                     │   day first
  └───────────────────────────────────┘
  ┌───────────────────────────────────┐
  │  4 March 2026                     │   month first
  └───────────────────────────────────┘

  We'll use your answer for the whole document.

  [ Show me where this appears ]           ← source view
```

**Term end (recurrence bound):**
```
  When does this schedule end?

  Weekly classes need an end date, otherwise
  they'd repeat forever.

  ┌───────────────────────────────────┐
  │  📅  Choose a date                │
  └───────────────────────────────────┘

  Common: end of this term, 15 weeks from now

  [ Skip — add as single events instead ]
```

The skip option matters. Forcing a date the user doesn't know is worse than degrading gracefully
to non-recurring events, and offering the degraded path openly is more trustworthy than
pretending recurrence is mandatory.

**Multiple schedules** *(later)*:
```
  4 timetables found

  Which one is yours?

  ┌───────────────────────────────────┐
  │  Semester 5 · Section A           │
  │  42 classes · Mon–Sat             │
  └───────────────────────────────────┘
  ┌───────────────────────────────────┐
  │  Semester 5 · Section B           │
  │  41 classes · Mon–Sat             │
  └───────────────────────────────────┘
  …

  Not sure? [ Preview each ]
```

### Success (pre-review)

```
        42 classes found

     CSE · Semester 5 · Section B

     ✓  40 ready
     ⚠  2 need review

  ┌───────────────────────────────────┐
  │       Review timetable            │
  └───────────────────────────────────┘

     Add 40 ready events without reviewing
```

The secondary action is deliberately worded to make the trade-off explicit. It is not a hidden
"skip review" — it says exactly what it skips and how many items it applies to. It is disabled
when unresolved items would make the result nonsensical.

### Review — the screen the product lives or dies on

```
┌─────────────────────────────────────┐
│  ←   Review timetable          ⋯    │
│                                     │
│  42 events    ✓ 40 ready  ⚠ 2 check │
│                                     │
│  [ All ]  [ Needs attention 2 ]     │   filter chips, sticky
│                                     │
│  MONDAY ─────────────────────────   │
│                                     │
│  ☑  09:00 – 10:00                   │
│     Data Structures                 │
│     Room K10                     ✓  │
│                                     │
│  ☑  10:00 – 11:00                   │
│     Operating Systems               │
│     Room K11                     ✓  │
│                                     │
│  ☑  11:00 – ?                    ⚠  │   the exception gets the weight
│     DBMS                            │
│     End time unclear                │
│     [ Set end time ]  [ View source ]│
│                                     │
│  TUESDAY ────────────────────────   │
│  …                                  │
│                                     │
├─────────────────────────────────────┤
│  40 selected      [ Continue ]      │   persistent bottom bar
└─────────────────────────────────────┘
```

Design rules:

- **Grouped by weekday** for recurring schedules, **by date** for dated schedules. The grouping
  matches how the user thinks about the document.
- **Ready rows are quiet.** No badge colour block, no card, no elevation. A small ✓ at the
  trailing edge. The row is legible in a glance and needs no interaction.
- **Attention rows carry the weight:** icon, a one-line plain-language reason, and inline
  resolution actions. No "tap for details" indirection — the fix is right there.
- **Selection is checkbox-based** and bulk-operable via long-press → select range, and via the
  overflow (select all / none / only ready).
- **The bottom bar always states what will happen.** "40 selected → Continue", never a bare
  "Next".
- Editing opens a bottom sheet with native pickers, not a form screen. Time picker, date picker,
  and a text field. Three fields maximum per sheet.

**Source view** (`View source`) is a bottom sheet showing the rendered document region with the
detected span highlighted:

```
  Where this came from

  Page 3
  ┌───────────────────────────────────┐
  │  Mon   09:00  Data Structures K10 │
  │  Mon  ▓11:00▓ DBMS               │   ← highlighted
  │  Tue   09:00  Operating Systems   │
  └───────────────────────────────────┘

  We found "11:00" but no end time in
  this row.

  [ Set end time ]
```

This screen does more for trust than any amount of confidence tuning. It converts "the app
claims" into "I can see it".

### Confirm

```
        You're about to add
             40 events

  Calendar    Personal (anshul@…)      ▸    ← tappable, required choice
  Dates       17 Aug – 5 Dec 2026
  Repeats     Weekly
  Reminder    10 minutes before        ▸

  ⚠  3 similar events already exist
     [ Review duplicates ]

  ┌───────────────────────────────────┐
  │        Add 40 events              │
  └───────────────────────────────────┘
              Cancel
```

The calendar row is never pre-filled with a guess. If the user has one writable calendar it is
pre-selected but still displayed; if they have several, they must choose.

### Done

```
             ✓

        You're all set.
        40 events added.

  ┌───────────────────────────────────┐
  │        Open Calendar              │
  └───────────────────────────────────┘

        View imported timetable

        ─────────────────────────
        Undo                              ← available for the session,
                                            and from History indefinitely
```

No rating prompt here. No upsell here. The user just finished a task; interrupting the moment of
relief to ask for money or stars is the single most common way this category earns 1-star
reviews. The purchase prompt comes later and elsewhere (*15-business.md*).

### Recovery screens

All failure states share one template: **plain statement → why (if known) → concrete next steps**.

```
        We couldn't read this PDF

  This document doesn't contain selectable
  text — it's probably a scan or photo.

  ┌───────────────────────────────────┐
  │   Read it as an image             │       ← OCR path
  └───────────────────────────────────┘
       Choose specific pages
       Try another file
```

Variants, each with its own honest cause line: damaged file, password protected, unsupported
format, empty file, too large, nothing actionable found, image too unclear.

Never: an error code, a stack trace, the word "failed", or a red screen. The tone is *this
document is difficult*, not *you did something wrong* and not *our software broke*.

## Interaction design

| Interaction | Behaviour |
|---|---|
| Primary CTA | Filled button, single per screen, bottom-anchored in flows |
| Destructive action | Requires a distinct confirmation naming what will be destroyed and how many |
| Editing a value | Bottom sheet, native picker, immediate apply, no Save button |
| Bulk selection | Checkbox + long-press range select + overflow presets |
| Filtering | Sticky chips; count shown on each; selecting a filter never loses selection state |
| Cancel | Always available during processing; always immediate; always confirms nothing changed |
| Undo | Snackbar for the session; permanent entry in History detail |
| Back from Review | Discard confirmation (work would be lost) |
| Back from Done | Returns Home, clears the flow stack |
| Pull to refresh | Not used. Nothing here is server-backed. |
| Swipe to delete | Not used in Review — too easy to lose an item you meant to edit. Explicit remove only. |

**Predictive back** is supported throughout (`android:enableOnBackInvokedCallback="true"`), with
proper back handlers on the flow steps so the preview animation shows the correct destination.

## Accessibility

Not a checklist item. This app produces a dense list of similar rows differentiated by state —
that is precisely the pattern that fails hardest for screen-reader and low-vision users.

### Requirements

| Area | Requirement |
|---|---|
| **Never colour alone** | Confidence uses glyph (✓ / ⚠ / ?) **and** shape **and** text. Verified by rendering the review list in greyscale — every state must remain distinguishable. |
| **Content descriptions** | Each review row announces as a sentence: *"Data Structures, Monday 9 to 10 AM, Room K10, ready, selected."* Not as five unlabelled fragments. |
| **State, not decoration** | Checkboxes use `Role.Checkbox` with `toggleableState`; filters use `selected` semantics, so TalkBack announces "selected" rather than the user inferring it. |
| **Live regions** | Processing stage changes announce politely (`liveRegion = Polite`). Completion announces assertively. |
| **Touch targets** | 48dp minimum for every interactive element, including the inline `View source` action on a dense row. |
| **Large text** | The review row must remain readable at 200% font scale. Test at 1.0/1.5/2.0. Rows grow; text never truncates the subject or the time. |
| **Contrast** | 4.5:1 for body, 3:1 for large text and meaningful icons, in both themes. |
| **Keyboard** | Full traversal order on tablets/Chromebooks/external keyboard; visible focus indicators; Enter activates. |
| **Reduced motion** | Respect the system animation scale. When it is 0, transitions become instant cross-fades, not shortened animations. |
| **Headings** | Weekday group headers carry `heading()` semantics so TalkBack users can navigate by heading instead of scrolling 42 rows. |

### The specific risk

A 42-row list where 40 rows are identical in structure is exhausting with a screen reader. So:

- The **"Needs attention" filter is the default entry point announced first** when unresolved
  items exist — a TalkBack user should be able to jump straight to the 2 rows that matter.
- Group headers are navigable landmarks.
- The bottom bar's "40 selected" is a live region, so bulk actions confirm audibly.

## Motion

Motion exists to explain state change. Nothing here is decorative.

| Transition | Treatment | Duration |
|---|---|---|
| Home → Import sheet | Standard M3 bottom sheet slide | 300ms emphasised-decelerate |
| Import → Processing | Shared container transform on the document card | 400ms emphasised |
| Processing stage advance | Checkmark fade + subtle scale on the completing line | 200ms standard |
| Processing → Success | Cross-fade with the headline count animating in | 300ms |
| Review row resolution | The ⚠ row settles to ✓ in place; the attention counter decrements with a number transition | 250ms |
| Confirm → writing | Progress replaces the button in place, same bounds | — |
| Write → Done | Checkmark draws once, no bounce, no confetti | 400ms |
| Undo | Snackbar, standard | — |

Forbidden: bouncing, floating cards, particle effects, sparkles, shimmer on content that isn't
loading, animated gradients, "AI thinking" animations. The product's credibility depends on
looking like a tool, not a toy.

**The one moment worth animating well** is the review-row resolution — the ⚠ becoming ✓ and the
counter dropping from 2 to 1. That is the user's progress made visible, and it is the only place
where a little delight is earned rather than applied.

All motion respects `Settings.Global.ANIMATOR_DURATION_SCALE`. At 0 the app is fully functional
with instant transitions.
